title: Domain mutations and revision concurrency
summary: "Every canonical change goes through a domain-specific, atomic mutation
  that requires the resource's current opaque `expectedRevision`; a stale
  revision writes nothing and reports the current revision, there is no generic
  file write, and out-of-band edits are detected. `/api/*` and `/mcp` are
  separate transport adapters over one shared application layer (MCP never calls
  `/api/*` over loopback HTTP), so HTTP, MCP and the Workbench share the same
  semantics. When the persistence lock wait budget expires, an operation changes
  nothing and fails retryably with `persistence.busy`: HTTP answers 503 with a
  `Retry-After` header, MCP returns an error result."
rules:
  - id: 01a1144e-508d-7f31-94f9-0c96b0ed4922
    statement: Canonical resources change only through domain-specific mutations,
      each atomic within one resource or domain boundary; a mutation may carry
      several structured operations against that boundary. There is no generic
      file write, arbitrary filesystem write or cross-domain Workspace-wide
      patch.
  - id: 01a1144e-50a1-7125-95ca-f757a8028ae7
    statement: "`/api/*`, `/mcp` and `/preview/*` are separate transport adapters
      over one shared application and domain layer: MCP never calls `/api/*`
      over loopback HTTP, and transport routes never duplicate domain logic."
  - id: 01a1144e-50b5-77f4-9403-493d7914702a
    statement: Edits made to canonical files outside UIUX are detected through
      content-derived revisions and validation, which survive process restarts;
      such edits bypass mutation-only affordances such as reference-impact
      acknowledgement.
  - id: 01a1144e-50c9-79f7-9530-479feba082fc
    statement: "When the persistence lock cannot be acquired within its wait budget,
      the operation changes nothing and fails retryably with `persistence.busy`:
      HTTP answers 503 with a `Retry-After` header, and MCP returns an error
      result."

## Notes
