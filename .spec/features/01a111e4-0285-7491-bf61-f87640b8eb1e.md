---
id: 01a111e4-0285-7491-bf61-f87640b8eb1e
title: Member roster and permission keys
summary: "The host-local member roster of each Workspace: where it is kept and
  how it is protected, its format upgrade, members with their kinds and explicit
  permission key sets, bootstrapping a first manager, carrying a roster over to
  a moved Workspace, and managing members and their keys from the CLI and the
  Workbench."
rules:
  - id: 01a11485-e9f5-79d8-a517-9d7e01321188
    statement: Each Workspace has exactly one roster on the host, identified by the
      real path of its root, so a symlink and its target share it; no roster
      serves two Workspaces, so the same person in two Workspaces is two
      independent members, possibly with different keys.
  - id: 01a11485-ea1b-7014-9111-62ca6c243342
    statement: A roster lives only on the host, under `$UIUX_HOME`, never in the
      Workspace or in Git, and it changes no canonical file, manifest field or
      `schemaVersion`; a copy of a Workspace therefore carries no members or
      credentials.
  - id: 01a11485-ea39-7069-abc5-410b7576f445
    statement: UIUX refuses a roster store that is a symlink, that is writable by
      group or others, or that records a Workspace root other than the one being
      served, and never silently reuses such a store.
  - id: 01a114ec-df62-74ec-bf6d-2571137c3576
    statement: Every roster write is atomic under the store's lock.
  - id: 01a11485-ea58-782e-9789-138833c868d9
    statement: "The CLI and a running server may both write a roster: the server
      re-reads it when it changes, at the check interval the Access Contract
      sets, so a CLI revoke, removal or key change takes effect on its next
      request without a restart."
  - id: 01a11c33-285a-70e0-86c1-ad2ee16751d1
    statement: "Roster administration works at every Workspace `schemaVersion`: a
      roster write is not a Workspace mutation, so a Workspace that needs
      migration or is unsupported never refuses it."
  - id: 01a11c09-b623-7824-8745-9c10510d0d53
    statement: The first UIUX process, server or CLI, that opens a version 1 roster
      upgrades it to version 2 once, atomically under the store's lock, keeping
      the backup that the Access Contract names.
  - id: 01a11c09-b698-7ee3-861b-f02eaba61269
    statement: The upgrade gives each member the keys that the Access Contract maps
      its role to, without `humanOnly` keys for an Agent, so no member's
      effective capabilities change.
  - id: 01a11485-ea75-7964-bc21-29aa78049abf
    statement: A member's kind, human or Agent, is fixed at creation, so an Agent
      can never be turned into a human to gain `humanOnly` keys.
  - id: 01a114ec-dfd0-7755-8454-64174ff0f327
    statement: A member's nickname is unique in its roster, ignoring case, and is
      its display name everywhere.
  - id: 01a11485-ea91-7107-b02e-f3db764e6d86
    statement: A holder of `members.manage` may rename a member or change its keys;
      records written earlier keep the name they were written with.
  - id: 01a11485-eaac-7523-998b-26123d7618df
    statement: "A member may do exactly what its stored keys allow: no key implies
      another, and each operation checks only the keys that the Access Contract
      assigns to it."
  - id: 01a11c09-b707-7138-91af-0542ea1b8b89
    statement: A member's key set is stored only when it holds every requirement, as
      the Access Contract lists them, of each key in it.
  - id: 01a11c09-b779-7f5f-ba47-170a584a09ce
    statement: A key set that lacks a requirement, written into a roster by hand,
      grants only the keys it lists.
  - id: 01a11c09-b7ec-786f-9723-eda32404d421
    statement: Keys unknown to the running UIUX version are kept when the roster is
      written and grant nothing.
  - id: 01a11485-eac6-730b-b66b-309cc9efb169
    statement: A `humanOnly` key, as the Access Contract marks it, is never stored
      on an Agent member.
  - id: 01a11c09-b85c-7d0b-a390-ca3dcd2e4a10
    statement: A holder of `members.manage` may give any member, itself included,
      any valid key set, even one with keys it does not hold.
  - id: 01a11485-eae3-7080-8f02-da27fc260e09
    statement: Every roster write that would leave no human member holding
      `members.manage` is refused, whether it removes a member or changes keys.
  - id: 01a11485-eaff-7339-91f9-10e9ea614b5b
    statement: Removing a member also removes its Tokens, invites and sessions, so
      none of them works after the server's next roster reload.
  - id: 01a11c09-b8c6-741e-b3b7-97f4840985c5
    statement: Applying a preset to a member, through the CLI or the Workbench,
      stores the keys it copies as they are at that moment, and no reference to
      the preset.
  - id: 01a11c74-26ef-7894-9b2c-2714f487aeb8
    statement: Applying a preset to an Agent member, through the CLI or the
      Workbench, copies the preset's keys without its `humanOnly` keys.
  - id: 01a11485-eb1a-77fb-a91e-b54c505344da
    statement: When `uiux dev` opens a roster where no human member holds
      `members.manage`, it creates a human member with every catalog key, named
      after the sanitized OS user name (or `owner`), and prints its sign-in link
      and Agent setup commands.
  - id: 01a114ec-e085-7353-bb10-6fa44d0e8cd5
    statement: Later starts print no bootstrap link, and startup never prints a Token.
  - id: 01a11c09-b9a6-70a6-a9f6-481c8c3f7386
    statement: The bootstrap output's command for adding an Agent names an existing
      preset, or `--keys` when the Workspace has no preset.
  - id: 01a11485-eb35-70b8-8c6b-b975f20f5b29
    statement: "UIUX does not detect a moved or renamed Workspace or a git worktree:
      a Workspace at a new real path starts with an empty roster and bootstraps
      its own manager, unless an old roster is carried over with `uiux access
      copy`."
  - id: 01a11485-eb50-7f42-85c4-6e524cb9c4b4
    statement: "A copied roster is independent of its source: it records the new
      Workspace root and gets its own roster hint, it carries no invites,
      sessions or last-used times, and later changes in either roster never
      reach the other."
  - id: 01a11485-eb6b-724e-b1cc-3f2bc59367e4
    statement: The roster's recorded Workspace root and hint are shown in the `uiux
      dev` startup output, by `uiux member list` and on the Workbench Members
      page.
  - id: 01a11c09-b932-7d3f-b006-7333c7127725
    statement: The CLI writes the roster with the host user's file access under the
      same invariants, so a host user can always restore a manager, for example
      with `uiux member set <nick> --grant members.manage`.
  - id: 01a11485-eb86-7a69-bf1b-70d492ee3be4
    statement: "Where 01a12500-b105-7773-822f-359d4dcbd1da serves roster
      administration, a signed-in holder of `members.manage` manages the served
      Workspace's roster on the Workbench Members page: adding, renaming,
      editing the keys of and removing members, creating Tokens (with a copy
      action) and revoking them, creating invites, and listing and revoking
      sessions."
  - id: 01a11485-eba3-7c07-a94f-0d69e610a0b6
    statement: The Workbench hides the actions that need a key the signed-in member
      lacks, or disables them and names the missing key; the server stays the
      authority.
  - id: 01a11c09-ba13-71f1-8194-898b221f6c8a
    statement: The Members page lists each member's nickname, kind, label, key
      count, Tokens and sessions.
  - id: 01a11c09-ba80-7bef-96fe-4a4bae3ab528
    statement: The Members page edits a member's keys in a checklist grouped by
      domain, with each key's identifier and description, a choice of preset to
      start from, and the resulting label shown as keys change.
  - id: 01a11c09-baec-71e2-b578-6efd9ee7ec98
    statement: The key checklist marks `humanOnly` keys as for humans only and
      disables them for an Agent, and checking a key also checks its
      requirements.
  - id: 01a11c09-bb58-7164-873e-c7882ce448a5
    statement: Where the Members page grants `members.manage`, it says that the
      holder can grant every key.
  - id: 01a11c33-24ab-76c8-8811-13d938153cad
    statement: The Members page flags a member whose key set lacks a requirement
      until that key set is next written.
  - id: 01a11c09-bbc9-721f-903c-27c615692624
    statement: The Members page shows holders of `members.manage` a notice listing
      the catalog keys that no human member holds, with links to the key
      checklist and to the Access presets page.
