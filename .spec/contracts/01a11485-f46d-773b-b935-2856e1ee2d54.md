id: 01a11485-f46d-773b-b935-2856e1ee2d54
title: Mutation and revision semantics
summary: "The semantics every canonical mutation shares on every transport
  (`/api/*`, `/mcp` and the Workbench): opaque content-derived revisions, the
  required `expectedRevision`, all-or-nothing conflicts that report the current
  revision, compact mutation results, the meaning of refusal statuses and the
  refusal codes of Review actions, how the shared result surfaces over HTTP and
  MCP, and the change events that commits emit to Workbenches."
clauses:
  - id: 01a11485-f4de-7bde-82f7-cbd5a550a7e7
    statement: Every mutable canonical resource has an opaque revision derived from
      its canonical content. Reads and queries return it; it is the same across
      process restarts and changes whenever that content changes, including
      through an edit made outside UIUX. Callers must not infer meaning from its
      representation.
  - id: 01a11485-f4fe-7329-9ac4-3fad1651a13b
    statement: Every mutation of an existing resource carries the `expectedRevision`
      its caller last read for that resource; a Review action carries its
      thread's.
  - id: 01a11485-f51c-7287-9b04-15b9d5a77238
    statement: A create carries no `expectedRevision`. It names or receives the
      identity of the new resource, and when a resource with that identity
      already exists it writes nothing and returns `already_exists`.
    constrains:
      - 01a111e4-0131-7584-bbfd-ca1afff5c2d8
      - 01a111e4-013a-798d-a808-3f242a1ac414
      - 01a111e4-015d-70aa-8098-a2bbe4690dc9
      - 01a111e4-0171-7cae-a37e-e67ec8deb82f
      - 01a111e4-01bb-783b-9792-a36016cd6c54
      - 01a111e4-01fb-7138-9e22-08b5ff81b735
  - id: 01a11485-f53a-7cde-94d9-eddaf72cf88d
    statement: When the resource's current revision differs from `expectedRevision`,
      the whole mutation writes nothing and returns a `conflict` result carrying
      `currentRevision`; the caller must re-read and decide again.
  - id: 01a11485-f55a-708e-baf7-9195d6514efc
    statement: A successful mutation returns its status, `created`, `updated` or
      `deleted`, and the affected identity. `created` and `updated` also return
      the new revision and diagnostics; `deleted`, the result of retracting a
      Review thread, carries no revision. A result never carries the whole
      Workspace.
  - id: 01a11485-f578-79a7-9d01-4bc233f2c1cb
    statement: "A successful mutation result also carries `changeSummary: { changes:
      [{ path, op }], truncated? }`, with `op` one of `add`, `remove` or
      `replace`, computed by diffing the resource's canonical content before and
      after the commit; caller-supplied text is never used."
  - id: 01a164f0-c0fe-7c86-9c50-cc9354e49fe8
    statement: A `changeSummary` `path` is a JSON Pointer relative to the resource
      root, at most 4 segments deep; a deeper difference folds into its
      4-segment prefix. An array whose elements are all objects with a unique
      string `id` is addressed by element id; any other array, or one whose kept
      elements change order, is reported whole as `replace`.
  - id: 01a164f0-c2a5-74dc-805d-c05ce25697d8
    statement: "`changes` is sorted by `path` in code unit order and holds at most
      50 entries; when more exist, `truncated` gives the number omitted."
  - id: 01a164f0-c44e-7d21-811d-93cbf7750dba
    statement: 'A `created` result lists every top-level member of the new resource
      as `add`, a `deleted` result gives the single change `{ path: "", op:
      "remove" }`, and an `updated` result whose content did not change gives
      empty `changes`.'
  - id: 01a164f0-c5fc-7b97-b21a-d127e423a157
    statement: "`changes` describes the primary resource; each other resource the
      same mutation writes is listed in `changeSummary.related` as `{ kind, key,
      revision, changes, truncated? }`, sorted by `kind` then `key`, with its
      `changes` sorted and capped like the primary's; the list itself is not
      capped."
  - id: 01a165fd-7ed3-7f80-aa0c-6989c9ce12b3
    statement: A promotion's primary resource is its thread, and the View that
      embeds the new Decision is its `related` entry, with
      `/spec/decisions/<id>` as `add`; an idempotent replay writes nothing and
      carries no `related`, and a history restore writes only its target and
      carries none.
  - id: 01a164f0-c7a4-7ec9-aa1e-71dfb5f26b53
    statement: "Every canonical resource mutation carries `changeSummary` on HTTP
      and MCP alike: View, Flow, Locale, Asset, Workspace settings, Review,
      Product Kit (compose, update, component registry), Access presets and
      single-resource history restore. Checkpoint create and delete carry none,
      and neither does a refusal."
  - id: 01a11485-f597-789e-b44b-a48a5582b62d
    statement: "Competing writes are never merged automatically, by implicit merge,
      CRDT or OT: the later writer gets a conflict and must re-read, retry or
      rework explicitly."
  - id: 01a11485-f5b6-77e1-b3bf-2a70ad33cc94
    statement: "Refusals are told apart by status: `conflict` means re-read,
      `blocked` means a precondition refuses the operation, and `locked` means
      another member holds an edit lease on the resource, so retry later or ask
      the holder."
  - id: 01a11485-f5d4-7950-b476-b471d961f332
    statement: 'A lease refusal is `{ status: "locked", key, code:
      "resource.locked", message, lock: { kind, key, holder: { nickname, kind },
      expiresAt } }`; it names the holder only by nickname and member kind.'
    constrains:

  - id: 01a114ec-e7f2-7956-ab12-91554f1b959e

    constrains:

  - id: 01a11485-f5f2-7e77-b32e-b2214e47b8d2
    statement: Over HTTP the structured result is the JSON response body; `conflict`
      and `already_exists` answer 409, and `locked` answers 423.
  - id: 01a11485-f610-78a7-a21a-d8c96d35e00e
    statement: Over MCP a tool returns the structured result as its structured
      content (and as JSON text), and any outcome other than success is an error
      result (`isError`).
    constrains:

  - id: 01a114ec-e839-7b11-957c-41c88b692e12

## Notes

- Why a Contract: agents and the Workbench depend on these semantics across HTTP, MCP and every authoring Feature, and they evolve independently of any one Feature.
- Owner ruling 2026-10-07 (checkpoint C), with its scope stated by the owner's calibration decision of 2026-10-07: "only HTTP 409, 423 and 403 are normative" applies to the HTTP statuses of mutation results only. Of those, `conflict` and `already_exists` answer 409 and `locked` 423 (01a11485-f5f2-7e77-b32e-b2214e47b8d2), and a role refusal answers 403 (01a11485-f9bd-78a3-a1d0-1b4f64e9883e). The ruling does not reach statuses fixed by other accepted decisions, which stay normative in the Clauses that own them: 401 and 429 (Discussion #1 c177; 01a11485-f999-7aea-86eb-51121a341c8b), 421, 403 and 415 of the baseline gates (ruling B4; 01a11485-f9df-73d4-9f47-85c9d559360c), 403 `access.admin_origin_rejected` (Discussion #174; 01a12500-a619-7fa5-b7f6-797adaf52f34), 422 for capture, assessment and export on a Workspace whose schema is unsupported (ruling B1, extended by Discussion #231 Change 1.2; 01a114ec-8931-798b-a550-5a918d013849) and 503 for `persistence.busy` (ruling B2; 01a114ec-e7f2-7956-ab12-91554f1b959e). The former 403 `auth.lan_not_allowed` was removed together with its Clause 01a11485-f6ca-7454-9c06-965899fca8b4, which Discussion #174 retired with the LAN listener design. The full result-status vocabulary and the HTTP status of every other result status (for example `created` 201, `updated` and `deleted` 200, `not_found` 404, `invalid` 400 and other `blocked` 422) are authoritative in code at a4160f8 (`src/server/authoring-http.ts`), as are result field shapes beyond the ones named here.
- The change-event stream is a Clause here because it carries the commits of every authoring Feature to the Workbench; there is no HTTP Contract (owner ruling Q4).
- Reference-impact acknowledgement for destructive changes is specified by Rules of the reference-integrity Feature (issue #75), not here.
- Import batch 4 adds the refusal codes of Review actions that accepted decisions name; the result status and HTTP status of each stay authoritative in code (see the first note).
- Part 11 (Discussion #122, decision 10 rules 1-2) adds Single-resource restore, 01a11a5d-fd6b-7f9d-be15-2bc2bc3adc13, to this Contract's scope: a restore is an ordinary revision-checked write with the shared result semantics.
