title: Mutation and revision semantics
summary: "The semantics every canonical mutation shares on every transport
  (`/api/*`, `/mcp` and the Workbench): opaque content-derived revisions, the
  required `expectedRevision`, all-or-nothing conflicts that report the current
  revision, compact mutation results, the meaning of refusal statuses, and how
  the shared result surfaces over HTTP and MCP."
clauses:
  - id: 01a11485-f4de-7bde-82f7-cbd5a550a7e7
    statement: Every mutable canonical resource has an opaque revision derived from
      its canonical content. Reads and queries return it; it is the same across
      process restarts and changes whenever that content changes, including
      through an edit made outside UIUX. Callers must not infer meaning from its
      representation.
  - id: 01a11485-f4fe-7329-9ac4-3fad1651a13b
    statement: Every mutation of an existing resource carries the `expectedRevision`
      its caller last read for that resource; a Review action carries its
      thread's.
  - id: 01a11485-f51c-7287-9b04-15b9d5a77238
    statement: A create carries no `expectedRevision`. It names or receives the
      identity of the new resource, and when a resource with that identity
      already exists it writes nothing and returns `already_exists`.
    constrains:
      - 01a111e4-0131-7584-bbfd-ca1afff5c2d8
      - 01a111e4-013a-798d-a808-3f242a1ac414
      - 01a111e4-015d-70aa-8098-a2bbe4690dc9
      - 01a111e4-0171-7cae-a37e-e67ec8deb82f
      - 01a111e4-01bb-783b-9792-a36016cd6c54
      - 01a111e4-01fb-7138-9e22-08b5ff81b735
  - id: 01a11485-f53a-7cde-94d9-eddaf72cf88d
    statement: When the resource's current revision differs from `expectedRevision`,
      the whole mutation writes nothing and returns a `conflict` result carrying
      `currentRevision`; the caller must re-read and decide again.
  - id: 01a11485-f55a-708e-baf7-9195d6514efc
    statement: A successful mutation returns its status (`created` or `updated`),
      the affected identity, the new revision and diagnostics, never the whole
      Workspace.
  - id: 01a11485-f578-79a7-9d01-4bc233f2c1cb
    statement: A successful mutation result also carries a summary of what changed.
  - id: 01a11485-f597-789e-b44b-a48a5582b62d
    statement: "Competing writes are never merged automatically, by implicit merge,
      CRDT or OT: the later writer gets a conflict and must re-read, retry or
      rework explicitly."
  - id: 01a11485-f5b6-77e1-b3bf-2a70ad33cc94
    statement: "Refusals are told apart by status: `conflict` means re-read,
      `blocked` means a precondition refuses the operation, and `locked` means
      another member holds an edit lease on the resource, so retry later or ask
      the holder."
  - id: 01a11485-f5d4-7950-b476-b471d961f332
    statement: 'A lease refusal is `{ status: "locked", key, code:
      "resource.locked", message, lock: { kind, key, holder: { nickname, kind },
      expiresAt } }`; it names the holder only by nickname and member kind.'
    constrains:
      - 01a111e4-0131-7584-bbfd-ca1afff5c2d8
      - 01a111e4-02c1-7229-b7e9-26110ee81a23
  - id: 01a11485-f5f2-7e77-b32e-b2214e47b8d2
    statement: Over HTTP the structured result is the JSON response body; `conflict`
      answers 409, `locked` 423 and a role refusal (`auth.scope_denied`) 403.
  - id: 01a11485-f610-78a7-a21a-d8c96d35e00e
    statement: Over MCP a tool returns the structured result as its structured
      content (and as JSON text), and any outcome other than success is an error
      result (`isError`).
    constrains:
      - 01a111e4-0131-7584-bbfd-ca1afff5c2d8
      - 01a111e4-02f2-7131-a974-233eb077d10b
  - id: 01a11485-f630-7a2c-8406-0497fa56d31b
    statement: HTTP and MCP run an operation through the same application service
      and return the same result for it; only the transport envelope differs.

## Notes

- Why a Contract: agents and the Workbench depend on these semantics across HTTP, MCP and every authoring Feature, and they evolve independently of any one Feature.
- Owner ruling 2026-10-07 (checkpoint C): only the HTTP statuses 409, 423 and 403 are normative here. The full result-status vocabulary and the HTTP status of statuses not named here (for example `created` 201, `not_found` 404, `invalid` 400, `blocked` 422) are authoritative in code at 20c427c (`src/server/authoring-http.ts`), as are result field shapes beyond the ones named here.
- Reference-impact acknowledgement for destructive changes is specified by Rules of the reference-integrity Feature (issue #75), not here.
